# CLAUDE.md — cosmetic-checker 開発ルール

化粧品の全成分表を撮影し、成分を**注意度1(緑)〜5(赤)**で色分け表示するRailsアプリ。
注意度は「刺激リスクの目安」であり、成分の安全/危険を断定するものではない。

> このファイルは開発を進めながら都度更新する。方針が変わったら、まずここを直す。

---

## 🚫 最優先ルール: `.claude/commands/plan-phase.md` の制約を厳守する

`/plan-phase` コマンドの実行中に限らず、すべての作業で `.claude/commands/plan-phase.md` の「厳守する制約」に従う。
このファイルと食い違う場合も、制約の厳しい方に従う。要点:

- Claude が指示なしで行ってよいのは「確認(読み取りのみ)」「現在のフェーズのプランファイルの作成・更新」「チャット画面への提示」の3つだけ
- **それ以外の修正は、ユーザーの明示的な指示なしに行わない**(ファイル編集、ブランチ操作、`git add` / `git commit`、ジェネレータ、マイグレーション、gem の追加など)
- **GitHub 上の処理は一切行わない**(push、PRの作成・マージ・クローズ、コメント、Dependabot への指示、設定変更など。指示があってもユーザー自身が行う)
- `git add` / `git commit` コマンド、issue のタイトル・本文、PRタイトル、PRメッセージは、チャット画面にコードブロックで提示する(issue・PR はテンプレートに従う。「Git運用ルール」参照)

## 開発方針(必ず守る)

### 役割分担

- **アプリのコードは本人が手で書く**(学習目的)。Claude は計画・解説・調査・レビューを担当する
- Claude はコードを書く代わりに、プランファイルに「ファイル名・行番号・修正前後・修正意図・確認コマンド」を示す(書き方は `plan-phase.md`)
- 本人が書いたあとは、Claude が `git diff` を読んでレビューする(バグ・規約違反・方針違反を指摘)

### Claude が編集してよいファイル / いけないファイル

| 区分                                         | 対象                                                                                                            |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| ✅ 指示なしで編集してよい                     | 現在のフェーズのプランファイル(`docs/development_plan/phaseN-xxx.md`)のみ                                    |
| ⚠️ 本人の指示があったときだけ編集してよい     | `.claude/CLAUDE.md` / `.claude/commands/*.md` / `docs/**/*.md`(`DETAILED_PLAN.md`・実装ログを含む)/ `README.md` / `.gitignore` |
| ❌ 本人が手で編集する(Claude は案を出すだけ) | 上記以外すべて(`app/` `config/` `db/` `test/` `bin/` `lib/` `.github/` `Gemfile` `Dockerfile*` `compose.yml` `.claude/settings.json` など) |

- ファイルやリポジトリの状態を変えるコマンド(`git switch` / `git pull` / `git add` / `git commit` / `bin/rails g` / `bin/rails db:migrate` / `bundle add` / `bundle update` など)は**本人が実行する**。Claude はプランファイルやチャットにコマンドを示す
- Claude が実行してよいのは確認系のコマンドのみ(`git status/log/diff`、`bin/rails test`、`bin/rubocop`、`bin/brakeman`、`bin/bundler-audit`、`bin/rails routes` など)
- GitHub 上の処理は行わない(最優先ルール参照)

### 作業ファイルの置き場所(すべて gitignore 対象・ローカル専用)

| 置き場所                | 用途                                                           |
| ----------------------- | -------------------------------------------------------------- |
| `docs/development_plan/` | プランファイル。`DETAILED_PLAN.md`(全体の計画)と、`/plan-phase` で作るフェーズごとの手順書 `phaseN-xxx.md` |
| `docs/development_log/`  | 実装ログ。本人の指示があったときに `YYYY-MM-DD.md` へ「やったこと・決めたこと・次にやること」を記録する |
| `.claude/commands/`      | Claude のコマンド(手順・実行範囲の指定)                     |

- これらは GitHub に上がらないため、`README.md` など公開ファイルからリンクしない
- 公開すべき仕様(注意度の判定基準など)は `docs/` 直下に置き、コミットする

## 用語と表現のルール(必ず守る)

UI・コード・コミットメッセージ・Gemini のプロンプト・ドキュメントすべてに適用する。

- 1〜5 の指標は **「注意度」** と呼ぶ。説明文では **「刺激リスクの目安」** と補足する
- **「危険度」「危険」「有害」「安全」「無害」は使わない**(断定的で不安をあおるため)
  - 例: ✕「危険な成分」 → ○「注意度が高めの成分」「刺激を感じる場合がある成分」
- コード上の名前は `caution_level`(`risk` / `danger` は使わない)
- **効能効果をうたう表現は禁止**: 「シミが消える」「シワが治る」「ニキビを防ぐ」「肌が若返る」「美白効果」「アンチエイジング」「医学的に証明」など
- 病気の治療・予防、身体の構造や機能への影響には触れない
- 特定の製品名・メーカー名を挙げて評価しない
- 根拠が不明な成分は注意度3とし、断定しない

## Git運用ルール(必ず守る)

### issue・ブランチ・PR

- **1 issue = 1ブランチ = 1PR**。作業は必ず issue を作ってから始め、issue番号をブランチ名に含める
- 1つのフェーズ(`DETAILED_PLAN.md` 上のまとまり)は、複数の issue に分割してよい
- **issue** は `.claude/commands/issue_template.md` の形式で書く。1 issue あたり **3P未満(6時間未満、2h=1P)** を厳守し、超える場合は分割する
- **PRメッセージ** は `.claude/commands/pr_template.md` の形式で、1つのコードブロック内に書く。「関連 issue」に `Closes #<issue番号>` を入れる
- issue・PR の作成は本人が GitHub 上で行う。Claude はタイトルと本文をチャット画面に提示する

### ブランチ命名規則

形式: **`<種類>/#<issue番号>-<説明>`**(例: `docs/#1-plan`)

| 種類        | 用途                                     | 例                               |
| ----------- | ---------------------------------------- | -------------------------------- |
| `feature/`  | 新機能・画面の追加                       | `feature/#3-ingredients-table`   |
| `fix/`      | バグ修正                                 | `fix/#12-fuzzy-search-threshold` |
| `hotfix/`   | 本番で起きている問題の緊急修正           | `hotfix/#15-scan-timeout`        |
| `refactor/` | 動作を変えないコードの整理               | `refactor/#20-lookup-service`    |
| `chore/`    | 依存関係の更新・CI・設定など             | `chore/#5-ci-deps`               |
| `docs/`     | ドキュメントのみの変更                   | `docs/#1-plan`                   |
| `test/`     | テストコードのみの追加・修正             | `test/#8-lookup-tests`           |
| `spike/`    | 技術検証(結果は issue にまとめ、マージしない) | `spike/#9-gemini-ocr`       |

- `release/` `merge/` などは、main 1本で運用する個人開発のため使わない
- 説明部分は**英小文字・数字・ハイフンのみ**。単語はハイフンで区切り、2〜4語程度で内容がわかるようにする
- 大文字・日本語・スペース・アンダースコア、`/` と `#` 以外の記号は使わない
- 1つのブランチに複数の issue の作業を混ぜない
- ブランチは最新の main から作成し、マージ後は削除する
- **コマンドではブランチ名を必ず引用符で囲む**(例: `git switch -c "docs/#1-plan"`)。`#` は zsh の設定(`extendedglob`)によって特別な記号として扱われるため

### コミット

- 1コミット=1つの意味のある変更。コミットメッセージは日本語で簡潔に
- `db:migrate` 後は `db/schema.rb` を、gem追加時は `Gemfile.lock` を必ずセットでコミット
- **`.env` は絶対にコミットしない**(APIキーが入っている)
- mainへの直接コミットはしない。必ずPR経由
- `git add`(ファイルを明記。`git add .` は使わない)/ `git commit` / `git push` のコマンドは Claude がチャット画面に提示し、実行は本人が行う

## 設計上の原則(必ず守る)

- **画像は保存しない**: アップロード画像はメモリ上でBase64化してGeminiへ送るのみ。Active Storageやtmp保存は使わない
- **画像の外部送信を明示する**: 撮影画面に「画像はGoogle(Gemini API)に送信され、本アプリでは保存しない」と表示する
- **キャッシュ優先の検索**: 「①DB完全一致 → ②pg_trgmあいまい検索 → ③Gemini APIで生成しDB保存」の順。②までで見つかればAPIを呼ばない
- **成分名は正規化してから検索・保存する**(NFKC+ひらがな→カタカナ+空白除去)
- **あいまい検索で別成分にすり替えない**: 類似度が高い場合のみ自動採用し、それ以外は「もしかして」候補として表示する
- **AI生成データの明示**: Gemini生成の成分情報は `ai_generated: true` を付け、画面に「AI生成」と表示する
- **出典と免責事項**: 成分詳細には出典(source / source_url)を表示。全ページに免責事項パーシャル(`shared/_disclaimer`)を表示
- 注意度の判定は @../docs/CAUTION_CRITERIA.md の基準に従う。根拠不明な場合はデフォルト3

## 実装しないこと

方針として**作らない**もの:

- 画像の保存(Active Storage・tmp・外部ストレージ)
- 製品(商品)単位の評価・ランキング・おすすめ表示、製品名やメーカー名での評価
- 効能効果の表示、肌診断・医学的な判断やアドバイス
- 成分を「安全」「危険」と断定する表示
- アフィリエイト・広告

今は**やらない**もの(将来の候補):

- ログイン・ユーザー登録・スキャン履歴
- 管理画面(当面の手動修正は seed / rails console で行う)
- Redisを挟んだ三層キャッシュ、出典・カテゴリテーブルの正規化
- CosIng等からの一括インポートバッチ

## コーディング規約

- 外部API呼び出しはサービスクラス(`app/services/`)に分離する
- API失敗時はアプリを止めず、該当成分のみ「情報を取得できませんでした」表示にする
- ビューの共通部品はパーシャル化する(バッジ・凡例・AI生成タグ・免責事項など)
- **色だけで情報を伝えない**: 注意度バッジには必ず数字を併記する。文字と背景のコントラスト比は4.5:1以上を目安にする(明るい背景色には濃い文字色)
